## 真实隔离 PostgreSQL 验证

新增的 16 项本机测试在实现前为 **15 failed / 1 passed**，缺失建库接口返回 405；实现后 **16 passed（7.08 秒）**，创建接口返回 201。所有写入位于隔离测试库，未修改实际业务库。

覆盖 8 个同键并发请求只产生 1 库、9 个不同创建请求在 5 库上限下仅 5 个成功和 4 个容量拒绝、同键不同名称冲突、改名后原创建请求重放、应用 lifespan 重新启动后的持久化、旧 `0002` 数据保留且不认领、额外字段/控制字符与来源拒绝、数据库 trigger 模拟提交失败不消费创建键，以及 downgrade 拒绝丢弃已使用的幂等记录。该轮 lifespan 重启与后续独立 API 进程重启分开记录。

最终补充改名提交失败的 trigger 回归，验证事务失败保留旧名称；17 项 M1 测试与直接提取当前 CI 内联 Python 的 1 项检查合计 **18 passed（10.58 秒）**。CI 内联检查运行在另一个全新隔离 PostgreSQL 上，证明本机执行结果；未触发 GitHub 工作流，不能据此记作远端 CI 通过。

## 真实浏览器与进程重启

在独立 PostgreSQL、FastAPI 与 Vite 上使用合成名称完成创建和改名，然后终止并重新启动该测试 API 进程；浏览器整页刷新后仍读到同一库及已修改名称，只有 1 个库、状态仍为 `empty`。这验证了实际进程重启后的业务持久化，不依赖浏览器内存或伪造的成功响应。既有 8000 服务未停止，模型 runtime 在测试环境中关闭。

桌面 1440×960 与小屏 375×812 截图已视觉检查，创建、改名和列表布局可用。本机截图为 `output/playwright/m1-knowledge-desktop.png` 和 `output/playwright/m1-knowledge-mobile.png`，属于忽略产物，不随仓库发布。

另完成真实网络故障注入链路：浏览器请求先通过 `route.fetch` 真实提交到 API，取得 201 并写入隔离 PostgreSQL，再截断发给浏览器的响应；整页刷新后由 `sessionStorage` 恢复“结果未知”的原创建请求。随后以错误 Origin 重放，后端真实返回 403，原键与名称只读状态仍保留；再次刷新后使用正确 Origin 手动同键重试返回 201。最终 API 核对该目标库仅 1 条、测试库总计 3 条，恢复记录已清空；`initiallyCommitted`、`forbiddenRetry`、`unique`、`recoveryCleared` 均为 true，未输出资源 ID 或响应正文。这是网络故障注入与真实 PostgreSQL 的联合结果，没有调用模型。

早先分步脚本用 `continue` 修改 Origin 未形成预期请求，且页面 HMR 干扰导致一次测试断言失败；冻结代码后改用 `route.fetch` 发出真实 403，完整链路重跑通过。该失败属于测试执行方式，没有据此伪报产品回归已复现或将未完成步骤计为通过。

- `0003_knowledge_management` 只在隔离测试库验证；实际业务库仍为旧迁移，现有服务不具有本片新增接口。使用新代码前需要另行安排显式迁移和重启，不能只刷新页面。

- `active_workspace` 尚未接入引擎实例选择，列为 M1-2 重建前置修复；当前未修复或验证。
- 本轮不验证真实模型质量、时延、Embedding 上限或引擎并发；后续供应商请求须先获明确授权。
- 前端 `sessionStorage` 只保留未确认创建所需的名称与请求键，整页刷新后由用户手动用同键重试；关闭标签页或清除浏览器存储后不保证恢复。该记录不是账号或服务端任务，也不保存模型凭证。
