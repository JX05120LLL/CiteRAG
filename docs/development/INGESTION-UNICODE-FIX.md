# 2026-09-26 Unicode 分块导致入库核验失败

## 根因与实际证据

只读核对独立验收库：Markdown 上传任务在索引阶段失败，后续重建任务在核验阶段返回 `rebuild_required`。失败重建的候选空间中，LightRAG 已将唯一文档标记为 `processed`；正文长度为 115,831 字符，55 个片段均有对应向量，文本与向量的正文、所属文档和来源一致。但其中 3 个片段包含分块产生的 Unicode 替代字符，不能逐字匹配受管原文。

固定 LightRAG 提交 `59af311307c7417b342f44850b097648d47e83bd` 的默认 Token 分块直接解码 Token 窗口。字节级 BPE 的窗口可能截断中文或其他多字节字符，产生 `U+FFFD`；CiteRAG 的 `content in normalized` 来源检查因此拒绝就绪。这解释了本次重建核验失败；更早上传阶段的同名错误码不能据此认定具有完全相同原因。

任务失败而资料仍显示 `indexing` 是另一项状态同步遗漏，修复证据见 [M1 验证记录](M1-VALIDATION.md)。本次处理分块根因，不放宽来源检查或伪造入库成功。

## 修复范围

- `backend/app/rag/sdk.py` 为引擎工厂注入 `chunking_by_source_span`。使用固定 SDK 已有的 `split_by_token_limit` 接口获得完整字符跨度，再直接切原文，不解码截断的 Token 窗口。
- 保持每片最多 1,200 Token、默认重叠 100 Token、六参数分块回调和分隔符模式；保持已验证跨度的边界空白，避免裁剪后 BPE 合并变化使 Token 数超限。跳过纯空白片段，不删除原文自身已有的替代字符。
- 不更换模型、不升级 SDK、不新增依赖、不改数据库 schema 或线上数据。既有片段不原地修补，原来的原文与索引核验继续生效。
- 回归测试放在已纳入当前 GitHub CI 的 `backend/tests/test_ingestion_jobs.py`；CI 不需要私有 tokenizer 文件或真实模型。没有触发远程 CI、提交或推送。

## 运行环境与重新验收

本轮未重启正在运行的验收 API，没有自动重试、重建、上传或发送真实模型请求，也没有修改用户已删除资料的状态。已运行进程中的引擎仍使用启动时的旧回调；修改须在验收 API 下次重启后加载。

集中验收步骤：

1. 完成当前页面工作后重启已确认归属的验收 API，保留原文目录和独立业务库配置。
2. 在验收页面重新上传原 Markdown；此前资料已经删除，需要新的上传任务，不能恢复已失效的历史任务。
3. 观察解析、建立索引、核验三个阶段。预期资料最终就绪，任务显示核验通过；就绪前不可问答。
4. 提问资料中的内容，打开引用核对正文位置。失败时保留任务阶段和安全错误码，不能仅凭此次离线分块通过认定真实模型端到端成功。

步骤 2—4 会产生真实供应商调用及费用，需在对应验收会话的授权范围内执行。本侧会话尚未运行这些步骤，因此真实 Markdown 重新入库与完整 M1 仍未验收通过。只读排查时失败候选空间仍有上述索引数据；本轮没有清理该空间，也没有验证所有失败候选空间的物理清理。
